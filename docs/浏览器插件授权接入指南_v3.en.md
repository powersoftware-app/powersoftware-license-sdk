# Browser Extension License Integration Guide (v3)

> For: publishing a product as a browser extension (Chrome Extension / Edge Add-on / Firefox Add-on, MV3) and integrating the license SDK to gate editions and paid features.
> Related: [Client Software License Integration Guide](客户端软件授权接入指南_v3.en.md) | [License SDK Spec](授权SDK规范_v3.en.md)

## 1. Why extensions can't get a machine code

Inside the browser sandbox, extension code cannot access any hardware identifier:

| Identifier | Client software (SDK `machineCode()`) | Browser extension |
|---|---|---|
| BIOS serial / MachineGuid / MAC | ✅ collectable | ❌ blocked by the sandbox |
| Hardware fingerprint (stable across reinstalls) | ✅ same machine, same code forever | ❌ no equivalent |
| Stable ID | hardware fingerprint + persisted UUID | only a self-generated Install ID |

So the extension's "machine code" **degrades to a plugin Install ID**: an `EXT-` prefix + a random UUID, generated once and persisted. The server auto-detects the `EXT-` prefix as the plugin type (`user_machine.machine_type = PLUGIN`); the activate/verify/purchase-redirect flow is **identical** to client software, with no server-side adaptation.

## 2. SDK installation

Copy the single file `node/src/webextension.js` into your extension project — dependency-free and directly bundleable (no Node modules; signing uses Web Crypto):

```
node/src/
├── index.js         Desktop/server client SDK (hardware-fingerprint machine code)
└── webextension.js  Browser-extension adapter (EXT- Install ID)  ← use this in extensions
```

manifest.json must declare the `storage` permission:

```json
{
  "manifest_version": 3,
  "permissions": ["storage"]
}
```

> `webextension.js` reuses the entire `LicenseClient` API surface from `index.js`, differing in only two ways: `machineCode()` becomes **async**; `sign()` is async (internal; integrators rarely touch it).

## 3. Core code

```js
// background.js (MV3 service worker)
import { LicenseClient, machineCode, deviceId } from './webextension.js';

const client = new LicenseClient({ productUniqueCode: 'PRO-2026-001' });

// ---------- First launch: claim trial ----------
async function claimTrial() {
  const mc = await machineCode();                       // async, returns EXT-xxxxxxxx-...
  const did = await deviceId();                          // async, returns DID-xxxxxxxx-... (trial anti-abuse, see 3.4)
  const result = await client.claimTrial(mc, did);       // did is sent as the x-device-id header; absent/invalid = not reported
  await saveCred({ licenseCode: result.licenseCode, activationToken: result.activationToken });
}

// ---------- Verify on paid-feature clicks (60s cache) ----------
async function checkLicense(requiredEdition = 'PRO') {
  const cred = await loadCred();
  if (!cred?.licenseCode) return { valid: false, reason: 'not activated' };
  try {
    const mc = await machineCode();
    const result = await client.verifyCached(cred.licenseCode, mc, cred.activationToken);
    if (!result.valid) return { valid: false, reason: 'license invalid or expired' };
    const levels = { BASIC: 0, PRO: 1, ULTIMATE: 2, TRIAL: 99 };
    if ((levels[result.edition] ?? 0) < levels[requiredEdition]) {
      return { valid: false, reason: `requires ${requiredEdition} or above` };
    }
    return { valid: true, edition: result.edition, expiryTime: result.expiryTime };
  } catch (e) {
    if (e.errorCode === 'machineLimit') return { valid: false, reason: 'machineLimit' };
    return { valid: false, reason: String(e) };
  }
}

// ---------- Activate after the user purchases and enters a code ----------
async function activate(licenseCode) {
  const mc = await machineCode();
  const result = await client.activate(licenseCode, mc);
  await saveCred({ licenseCode, activationToken: result.activationToken });
}

// ---------- Purchase redirect (auto-carries the EXT- code; ordering binds it to the buyer) ----------
function openPurchasePage(mc) {
  chrome.tabs.create({ url: client.purchaseUrl(mc) });
}
```

Local credential persistence follows the same rule as client software (store only `licenseCode` + `activationToken` + the last verify result), but the **storage location differs** — see the next section.

### 3.1 Trial quota (trialCount / trialCountPeriod)

The extension's trial dimension follows the same rule as client software: the platform **no longer presets a default quota for plugin-form products** — set the trial quota explicitly on the publish page (when `TRIAL_FIRST` + usage-based `QUOTA` is left unconfigured, the platform falls back to a default of 20; trial days may be 0) — a "trial by quota" mode alongside time-based trials:

- `claimTrial` / `activate` / `verify` success responses return `trialCount` (product-level config; `null` when disabled), plus `trialCountPeriod` (`TOTAL` cumulative, default, matching legacy / `DAILY` / `WEEKLY` (ISO-8601 calendar week) / `MONTHLY` reset each calendar day/week/month) and `trialPeriodKey` (delivered only for reset-type periods, the server's current period key, e.g. `DAILY="2026-09-30"`, `WEEKLY="2026-W39"`, `MONTHLY="2026-09"`);
- **The platform records no usage**: decrementing and resetting are done locally by the extension (prefer `chrome.storage.local`; to persist across browser instances you may mirror to `storage.sync`) — local bookkeeping can't stop quota from being refreshed by reinstalling or used on several devices, see §3.2;
- **Reset rule**: persist local usage as `{ periodKey, used }`; when the stored `periodKey` differs from the latest `trialPeriodKey`, reset and recount. The period comes from the server key — **never compute the day/week/month from `Date.now()`** (a rewound clock would reset early); each period's quota never rolls over;
- When the quota reaches zero, treat the trial as ended (guide to purchase like `expired`);
- It's product-level and independent of billing period (periods don't accumulate); if both `trialDays` (time) and `trialCount` are set, whichever comes first ends the trial;
- **Usage-based quota products (`licensePricingModel = QUOTA`)**: if the product is sold as quota packs on the publish page, `activate` / `verify` responses additionally return two quota fields: `quotaAmount` (the quota on **this one code** — under `SAME_CODE` a repurchase on the same machine has already accumulated onto it) and `quotaTotal` (**the sum over every valid code of this product bound to the same machine code**). **Prefer `quotaTotal` as the usable balance**: accumulation only hits when the upgrade mode is `SAME_CODE`, the order carried a machine code, and that machine already holds a valid code of the same edition; every other case (`NEW_CODE`, an order placed from the web without a machine code, repurchase on another machine) issues an extra independent code, and reading one code's `quotaAmount` alone then shows "paid for two packs, see one". Cache entries written before the field existed have no `quotaTotal` — fall back to the old rule (`SAME_CODE`: use `quotaAmount`; `NEW_CODE`: sum the codes yourself). **For paid quota (`quotaAmount`/`quotaTotal`), report consumption to the platform's `POST /license/quota/consume` (SDK `consume(...)`) and treat the machine-level `quotaRemaining` it returns as the only trusted balance** (see §3.2); the free `trialCount` quota is still booked locally by the extension for now. See §3.9 of the client-software guide.

### 3.2 One code across browsers and laptops: local bookkeeping can't stop multi-fold consumption (important)

An extension can't read a hardware machine code, so the Install ID stands in for `machineCode` while usage lives in `chrome.storage.local`. The result: **every device / browser instance holding the same license code keeps its own full copy of the balance**.

| Symptom | Cause | Consequence |
|---|---|---|
| Home and work both burn the full 100 uses of one 100-use pack | Two independent local `used` counters that never meet | Sold 100 uses, actually delivered 200 |
| Quota comes back "full" after a reinstall or clearing browsing data | `storage.local` wiped, `used` resets | Resetting the extension refreshes the quota for free |
| Editing storage gives unlimited quota | No trusted execution environment on the client | Local bookkeeping is not a basis for billing |

What the platform already provided only caps **machine count** (`maxMachines`) — it does not cap **consumption rate**: the code's own `quotaAmount` answers "how much this code bought", not "how much has been spent". **The platform has now shipped a consumption-accounting endpoint, `POST /license/quota/consume` (SDK `consume(...)`, same family as `verify`, authenticated by `activationToken`), which lifts "how much has been spent" out of local storage and onto the server**, curing multi-fold consumption:

- Usage lives in the server's `license_usage` lots/buckets table, **keyed on `licenseCode` (not the Install ID)**, so one code shares a single balance across browsers / laptops / reinstalls and stops at zero — reinstalling or clearing browsing data no longer "refreshes" the quota; paid quota is granted as **lots** (each with its own `cap` + `expires_at`), consumption deducts the **earliest-expiring live lot first (FIFO)** among unexpired lots with room, and `quotaRemaining = Σ (cap - used)` over live lots; **the code is never marked `expired` by quota** (exhausting or expiring all lots only drives `remaining=0` to prompt repurchase);
- Each billable action calls `consume(licenseCode, machineCode, activationToken, amount, requestId, kind)` (`amount` is a positive number, decimals allowed — e.g. `0.5` for token/time metering; `kind` defaults to `'quota'`; pass `'trial'` for trial quota, which is server-accounted in period buckets); the server performs a **per-lot atomic bounded decrement** on the selected lot (`used + take <= cap` and the lot unexpired, charged only against the current code's lots, never its machine siblings) and returns the lot-aggregated `quotaRemaining` (or `trialRemaining`) as the **only trusted balance**; local `used` becomes an offline display cache and is no longer the gating basis;
- Idempotency: `requestId` (8–128 chars, client-generated) is de-duplicated server-side so retries can't double-charge; a concurrent same-`requestId` request returns `quotaConsumeProcessing`, and an exhausted balance returns `insufficientQuota`;
- Balance alignment: startup `verify` now returns the code's `quotaUsed` / `quotaRemaining` (lagging at most one cache TTL) to reconcile local display; the immediate `consume` return is the most accurate balance;
- Offline / weak network: allow a small local grace allowance (e.g. ≤ 5 calls), then batch-report each with its own `requestId`; accept that the grace window may leak a few uses; once exhausted the extension must come back online and succeed at `consume` to continue.

The free trial quota (`trialCount`) still follows the local period rule of §3.1 and does not use `consume` for now.

### 3.3 Field × pricing-model mapping (EDITION / QUOTA)

Not every `verify` / `activate` / `consume` response field is meaningful for both pricing models. Each product picks one (product-level `licensePricingModel`); **fields not applicable to the current model are always `null`**, so render `-` defensively:

| Field | Model | Notes |
| --- | --- | --- |
| `licenseCode` / `machineCode` / `activationToken` / `status` | Common | License code / machine code (Install ID for extensions) / activation token / status |
| `productUniqueCode` / `source` / `maxMachines` / `activatedMachines` | Common | Product code / issue source / machine cap and bound count |
| `edition` | Common (differs in meaning) | EDITION: tier; QUOTA: always a single Basic edition (may be `null`) |
| `softwareMajorVersion` / `trialDays` / `trialExpiryTime` / `licenseDeductionEnabled` | EDITION | Major version / day-based trial / grace snapshot / upgrade proration |
| `billingPeriod` | **Dual meaning** | EDITION→subscription period (drives code `expiryTime` / renewal); QUOTA→per-lot validity period (per-lot `expires_at`) |
| `quotaAmount` / `quotaUsed` / `quotaRemaining` / `quotaNextExpiry` | QUOTA | Display total / used / remaining / quota expiry; **`quotaAmount` is always `null` for EDITION** |
| `trialCount` / `trialCountPeriod` / `trialPeriodKey` / `trialUsed` / `trialRemaining` / `trialNextResetTime` | QUOTA | Per-use trial quota / period / bucket key / used / remaining / next reset time; **always `null` for EDITION** |
| `consume` (`kind: 'quota' \| 'trial'`) | QUOTA | Quota-consumption endpoint; EDITION never calls it |

> Key points: `billingPeriod` is dual-meaning. Gate on `quotaRemaining` only (`consume`'s immediate return is freshest; `verify` lags at most one cache TTL); read quota expiry from `quotaNextExpiry` (when `null`, infer "perpetual" / "used up" off `quotaRemaining`).

### 3.4 Device identifier `x-device-id` (trial anti-abuse, reporting recommended)

The server runs a device + subnet anti-abuse review on trial claims (`claimTrial`). **Recommended**: send the optional `x-device-id` header. Omitting it does not error, but the server can then only fall back to the subnet dimension, and a missing/anomalous report may shorten this claim's grant.

**Why not reuse the Install ID (`machineCode`) as the device id**: `machineCode` (`EXT-` Install ID) lives in `storage.sync` and **follows the Chrome account**, so home/work machines get the same ID — it represents "this person's browser identity". The device gate needs to tell "many devices, one install each" apart, so it wants an identifier **bound to the physical browser**, not synced across devices. The two serve different roles.

**Default generation (SDK `deviceId()`)**: on first run it creates `DID-` + `crypto.randomUUID()` and persists it only to `chrome.storage.local` under `psDeviceId` (**no sync**, to avoid replicating to other machines and falsely tripping anti-abuse); the format is always `DID-<uuid>`, matching the server whitelist regex `^DID-[A-Za-z0-9_-]{6,64}$`. Clearing browser data resets it (treated as a new device, acceptable):

```js
import { deviceId } from './webextension.js';
const did = await deviceId();            // DID-xxxxxxxx-xxxx-...
await client.claimTrial(mc, did);        // the SDK puts did into the x-device-id request header
```

**Optional hardening: survive uninstall** (same effect as the official extension's `ps_did` first-party cookie): `storage.local` is wiped on uninstall; to keep the device id stable across uninstall/reinstall, write a first-party cookie on the API host instead (cookies live in the browser profile and are not cleared by uninstalling the extension). This needs `cookies` permission + `host_permissions` in the manifest:

```json
{
  "manifest_version": 3,
  "permissions": ["storage", "cookies"],
  "host_permissions": ["https://www.powersoftware.app/*"]
}
```

```js
// Try the ps_did cookie first; if absent, mint DID-<uuid> and write it (long expiry, survives uninstall)
async function deviceIdViaCookie(url = 'https://www.powersoftware.app') {
  const existing = await chrome.cookies.get({ url, name: 'ps_did' });
  if (existing?.value && /^DID-[A-Za-z0-9_-]{6,64}$/.test(existing.value)) return existing.value;
  const did = 'DID-' + crypto.randomUUID();
  await chrome.cookies.set({ url, name: 'ps_did', value: did, expirationDate: Date.now() / 1000 + 60 * 60 * 24 * 365 * 5 });
  return did;
}
```

> Pick either path: ordinary integrations just use the SDK `deviceId()`; use the cookie variant when you need cross-uninstall stability. Either way, pass it as the 2nd argument to `claimTrial(mc, did)` and the SDK sets the `x-device-id` header.

## 4. Install-ID persistence strategy

`machineCode()` already writes to both stores internally; integrators don't handle it, but should understand its behavior:

| Store | Role | When it's lost |
|---|---|---|
| `chrome.storage.local` | baseline, stable within this browser instance | uninstalling the extension / clearing browser data |
| `chrome.storage.sync` | follows the user's Chrome account, **same ID across devices** | signing out and clearing synced data |

Read priority: `sync → local → newly generated`; on conflict `sync` wins (follows the account).

**In practice**: when the user is signed into Chrome, home/work machines and browser reinstalls all keep the same Install ID — effectively upgrading "a browser instance" to "this person's Chrome identity" for free.

## 5. Handling reinstall after deleting the extension (important)

### 5.1 Three scenarios

| Scenario | Install ID | Local credential (licenseCode/token) | User experience |
|---|---|---|---|
| Reinstall, **signed into Chrome** | ✅ unchanged (restored from sync) | ❌ lost (cred is local-only) | needs one re-activation |
| Reinstall, **not signed in** | ❌ becomes a new ID | ❌ lost | needs re-activation, may hit the machine limit |
| Only cleared browsing data, extension intact | ❌ local lost; unchanged if in sync | ❌ lost | same as above |

**Takeaway: by any design, the local credential is lost after a reinstall. The real issue isn't "can't recognize the same machine" but "can't recognize the same user" — so anchor identity on the license code / account, not the device.**

### 5.2 Recommended: mirror licenseCode into storage.sync

Also sync the license code (not a secret) to `storage.sync`, so after reinstall activation **auto-restores with zero user input**:

```js
const CRED_KEY = 'psLicenseCred';

async function saveCred(cred) {
  // write token + licenseCode to both local and sync
  await chrome.storage.local.set({ [CRED_KEY]: cred });
  await chrome.storage.sync.set({ [CRED_KEY]: cred }).catch(() => {});
}

async function loadCred() {
  const local = (await chrome.storage.local.get([CRED_KEY]))[CRED_KEY];
  if (local) return local;
  // after reinstall / data clear: restore from sync
  const synced = (await chrome.storage.sync.get([CRED_KEY]))[CRED_KEY];
  if (synced) {
    await chrome.storage.local.set({ [CRED_KEY]: synced });
    return synced;
  }
  return null;
}
```

Startup flow after a reinstall:

```
extension starts
  │
  ├─ loadCred() restored a licenseCode from sync?
  │     ├─ yes → activate(licenseCode, new Install ID) silently re-binds
  │     │        ├─ success → activation restored, user unaware
  │     │        └─ machineLimit → go to the §5.3 unbind guidance
  │     │
  │     └─ no → show the activation screen: enter a code / go to the purchase page
  │
  └─ verifyCached passes → normal use
```

> **Note**: silent re-activation requires spare machine-binding capacity (the new Install ID ≠ old ID case, i.e. the user is not signed into Chrome). A signed-in user's ID is unchanged and passes directly.

### 5.3 machineLimit: bindings full

Users who aren't signed in generate multiple `EXT-` IDs on repeated reinstalls; when a code's bound machines reach `maxMachines`, `activate`/`verify` return `machineLimit`. Handle it with your usual copy:

```js
if (result.valid === false && result.reason === 'machineLimit') {
  showPage(`
    Device binding limit reached.
    1) Open your profile center, unbind unused devices, and retry;
    2) If you just reinstalled and are signed into Chrome, re-logging in auto-restores the Install ID.
  `);
}
```

Unbind paths (shared with client software):

- **Profile center**: users self-unbind old devices;
- **SDK `deactivate(code, mc)`**: offer an "unbind this device" button in extension settings (requires login);
- **Rebind quota**: after a self-unbind you can't unbind again for 30 days (a platform limit against malicious rebinding), error code `unbindQuotaExceeded`.

### 5.4 How "extension machine codes" look platform-side

- The server auto-classifies the `EXT-` prefix as `machineType=PLUGIN`; the admin machine-code page supports filtering by type;
- When ops troubleshoot: for extension users "one device" = one browser instance (not signed in) or one Chrome account (signed in), which is **not** a physical computer — mind the wording;
- Risk control: many **new** `EXT-` IDs activating against one code in a short window usually means repeated reinstalls while signed out, or malicious sharing; verify manually and adjust the binding limit if needed.

## 6. Error-code handling

Identical to client software (`codeNotFound` / `revoked` / `expired` / `machineLimit` / `tooManyAttempts` / `trialNotEnabled` / `trialAlreadyPurchased` / `NETWORK_ERROR`); see [Client Software License Integration Guide · error codes](客户端软件授权接入指南_v3.en.md#8-error-code-handling). Extension-specific notes:

- MV3 service workers sleep at any time, so the **60s verify cache expires with the worker lifecycle** — this is normal and needs no handling;
- On `NETWORK_ERROR`, consider an offline grace using the last verify result (add your own window, e.g. 72h).
