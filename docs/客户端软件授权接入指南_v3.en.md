# Client Software License Integration Guide (v3)

> For: publishing client software on PowerSoftware and integrating the license SDK to gate editions and paid features.
> SDK repo: [github.com/mizhanchengxi/powersoftware-license-sdk](https://github.com/mizhanchengxi/powersoftware-license-sdk)
> Related: [License SDK Spec](授权SDK规范_v3.en.md) | Sales model & license purchase flow

## 1. Two integration scenarios

PowerSoftware offers two ways to integrate licensing for client software; pick by your situation:

| | Scenario A: Full platform flow (trial-first) | Scenario B: Orders off-platform |
|---|---|---|
| **Applies to** | Client software with the `TRIAL_FIRST` sales model | Client/server software, you collect payment yourself |
| **Who collects payment** | PowerSoftware platform (Alipay / PayPal) | You (in-app payment or other channels) |
| **Who issues license codes** | Platform issues automatically after payment succeeds | Software calls the platform API (HMAC-signed) |
| **`apiSecret` needed?** | ❌ No | ✅ Yes (server-side only, never in the client) |
| **Backend needed?** | ❌ No, pure client is enough | ✅ Yes (holds `apiSecret`, forwards issuance) |
| **Trial license** | ✅ Supported (`claimTrial`) | ❌ No trial |
| **Purchase page** | Provided by platform; one-line redirect | No platform purchase page; you handle it |

> **On edition config**: every product form (client/server/promotion-only) can enable license codes and define custom editions (BASIC/PRO/ULTIMATE, etc.). Edition prices and feature lists are shown on the purchase page only when you check "platform-collected license fee" (`licensePlatformPayment`); if unchecked, you handle payment yourself and the platform only provides code issuance and verification.

### How to choose

- **Indie dev / small team without your own backend** → pick **Scenario A**
- **You already have a payment channel (WeChat/Alipay merchant, etc.) and only want platform issuance/verification** → pick **Scenario B**

## 3. Scenario A: full platform flow (trial-first)

### 3.1 Prerequisites

1. Publish the product on PowerSoftware and choose the **TRIAL_FIRST** sales model
2. Set trial days (e.g. 7)
3. Configure license editions — three tiers by default, customizable:
   - `BASIC` — Basic
   - `PRO` — Pro
   - `ULTIMATE` — Ultimate
4. Check "platform-collected license fee" (mandatory for TRIAL_FIRST; optional for PAY_FIRST)
5. Note down `productUniqueCode` (visible on the publish page, not a secret)

### 3.2 Initialization

**No `apiSecret` required.** `apiSecret` is only for Scenario B's signed issuance; Scenario A never uses it.

```python
mc = machine_code()
```


### 3.3 Full flow

```
First launch
    │
    ├─ claimTrial(machineCode) ──────────────────→ obtain a trial license
    │     ↓ returns { licenseCode, activationToken, licenseUpgradeMode }
    │     ↓ persist locally
    │
    ├─ During trial: all features available
    │     │
    │     └─ Paid-feature click → verifyCached() (60s cache) → allow
    │
    └─ Trial expired / not activated
          │
          ├─ verifyCached() returns invalid/expired
          ├─ Prompt "purchase & activation required"
          └─ purchaseUrl(machineCode) → open platform purchase page
                │
                ↓ user pays on the platform
                │
                ↓ platform issues the code + email delivery
                │
          user returns, enters the license code
                │
                ├─ activate(licenseCode, machineCode)
                │     ↓ returns { activationToken, licenseUpgradeMode }
                │     ↓ persist locally
                │
                └─ later use → verifyCached() → allow
```

### 3.4 Core code

```python
import json
from pathlib import Path
from ps_license_sdk import LicenseClient, machine_code

# ---------- Init ----------
client = LicenseClient(product_unique_code="PRO-2026-001", api_secret="")
CRED_FILE = Path.home() / ".myapp" / "license.json"

def load_cred():
    if CRED_FILE.exists():
        return json.loads(CRED_FILE.read_text())
    return {}

def save_cred(d):
    CRED_FILE.parent.mkdir(parents=True, exist_ok=True)
    CRED_FILE.write_text(json.dumps(d, ensure_ascii=False))

# ---------- First launch: claim trial ----------
def claim_trial():
    mc = machine_code()
    try:
        result = client.claim_trial(mc)
        save_cred({
            "licenseCode": result["licenseCode"],
            "activationToken": result["activationToken"],
        })
        print(f"Trial activated, license code: {result['licenseCode']}")
    except Exception as e:
        print(f"Failed to claim trial: {e}")

# ---------- Verify license (call when a paid feature is clicked) ----------
def check_license(required_edition="PRO"):
    cred = load_cred()
    if not cred.get("licenseCode"):
        return {"valid": False, "reason": "not activated"}

    mc = machine_code()
    try:
        result = client.verify_cached(
            cred["licenseCode"], mc, cred["activationToken"]
        )
        if not result.get("valid"):
            return {"valid": False, "reason": "license invalid or expired"}

        user_edition = result.get("edition", "")
        # TRIAL license = all features unlocked; give it the highest level
        # (omitting TRIAL from the map would leave only basic features during the trial!)
        levels = {"BASIC": 0, "PRO": 1, "ULTIMATE": 2, "TRIAL": 99}
        if levels.get(user_edition, 0) < levels.get(required_edition, 0):
            return {"valid": False, "reason": f"requires {required_edition} or above"}

        return {"valid": True, "edition": user_edition,
                "expiryTime": result.get("expiryTime"),
                "trialExpiryTime": result.get("trialExpiryTime")}
    except Exception as e:
        return {"valid": False, "reason": str(e)}

# ---------- Activate a license code (after the user purchases) ----------
def activate(license_code):
    mc = machine_code()
    try:
        result = client.activate(license_code, mc)
        save_cred({
            "licenseCode": license_code,
            "activationToken": result["activationToken"],
        })
        return True
    except Exception as e:
        print(f"Activation failed: {e}")
        return False

# ---------- Open the purchase page ----------
def open_purchase_page():
    mc = machine_code()
    url = client.purchase_url(mc)
    import webbrowser
    webbrowser.open(url)
```

### 3.5 Feature-gating example

```python
# Required edition per feature
FEATURE_EDITION = {
    "basic_feature":   "BASIC",
    "plus_feature":    "PRO",
    "ultimate_feature": "ULTIMATE",
}

def run_feature(feature_name):
    required = FEATURE_EDITION.get(feature_name, "BASIC")
    if required == "BASIC":
        do_basic_feature()
        return

    result = check_license(required)
    if result["valid"]:
        do_paid_feature(feature_name)
    else:
        print(f"Cannot use this feature: {result['reason']}")
        open_purchase_page()
```

### 3.6 Trial-to-purchase feature grace (trialExpiryTime)

During the trial, a trial-first product is **fully featured**. After the user buys a lower edition, higher-tier features are gated off immediately, creating a "paid but lost features" gap. To bridge it, the activate/verify/claim-trial success responses all return `trialExpiryTime` (the original trial license's expiry, ISO 8601; `null` when not a trial-to-purchase):

- On trial-to-purchase (upgrade of the original code or a new code), the platform first looks up the trial's original expiry and freezes it into this field; after purchase `expiryTime` becomes the bought edition's validity while this field stays unchanged;
- Expired trial-to-purchase also records it (a past timestamp), usable to detect "no grace";
- Later paid upgrades/renewals keep the field.

Clients decide their own transition policy, e.g. keep higher-tier features until the trial expiry (a grace period), then lock them and prompt to pay the difference to upgrade:

```python
def feature_allowed(check_result, required_edition="ULTIMATE"):
    """When the edition is insufficient, still allow higher-tier features before the original trial expiry."""
    if check_result["valid"]:
        return True
    levels = {"BASIC": 0, "PRO": 1, "ULTIMATE": 2}
    if levels.get(check_result.get("edition", ""), 0) >= levels[required_edition]:
        return True
    trial_expiry = check_result.get("trialExpiryTime")
    if not trial_expiry:  # not a trial-to-purchase, or trial expired: no grace
        return False
    from datetime import datetime, timezone
    return datetime.now(timezone.utc) < datetime.fromisoformat(trial_expiry.replace("Z", "+00:00"))
```

Whether to use this field, and how (duration, UI hints, countdown to upgrade) is entirely up to the client; the platform does not enforce it.

### 3.7 Billing period & renewal extension (billingPeriod)

Editions support three billing periods: `PERMANENT` (lifetime buyout, default), `MONTHLY` (fixed 30 days), `YEARLY` (fixed 365 days). Purchase-page prices show a period suffix (`/mo`, `/yr`; none for lifetime), and expiry-reminder emails are sent automatically 7 days before expiry.

What this means for integration:

- **`expiryTime` semantics**: for periodic editions, `verify`/`activate` return a fixed expiry date (ISO 8601); after it passes, verify returns the `expired` code — handle it with your existing expiry prompt. Lifetime `expiryTime` is `null`. Clients neither need to nor can detect the period type from the SDK APIs; to show a "monthly/yearly" badge use the purchase-page edition config.
- **In-app upgrade/renewal with a period**: when one edition has multiple billing-period rows, `upgradeForSoftware` accepts an optional `billingPeriod` (`PERMANENT`/`MONTHLY`/`YEARLY`) to choose the target row; default is the edition's first configured row. Periodic upgrades extend by `base = max(now, old expiry)` — see SDK spec §3.0.
- **Renewal extension**: renewing before expiry (platform purchase page or in-app) automatically extends from the **original expiry** (`base = max(now, old expiry)`) so no remaining time is lost; renewing after expiry starts from now. Neither the SDK nor your code needs to do anything — it's implemented platform-side.
- **Expiry reminders**: the platform scans daily and emails reminders for periodic codes expiring within 7 days (guiding in-app renewal); the SDK need not be aware.

### 3.8 Trial quota (trialCount / trialCountPeriod)

A second trial mode alongside time-based `trialDays`: the product can configure a **trial quota** (product-level, independent of billing period, not summed across periods), suited to plugins that "consume trial quota per feature call".

- **Where to configure**: the "trial quota" field on the publish page — it exists **only for products published under the usage-based quota model (`licensePricingModel = QUOTA`)**; edition-tiered (`EDITION`) products trial by days only and expose no trial-quota field (the platform also no longer presets a default 20 for plugin-form products). Once enabled you can pick a **quota period**: cumulative (`TOTAL`, default, ends when used up), reset daily (`DAILY`), reset weekly (`WEEKLY`, ISO-8601 calendar week), or reset monthly (`MONTHLY`, calendar month).
- **How it's delivered**: `claimTrial`/`activate`/`verify` success responses return `trialCount` (product-level config, the grant `cap` template; `null` when disabled), plus `trialCountPeriod` and `trialPeriodKey` (for reset-type periods `DAILY`/`WEEKLY`/`MONTHLY`, the server's current period key, e.g. `DAILY="2026-09-30"`, `WEEKLY="2026-W39"`, `MONTHLY="2026-09"`; `null` for `TOTAL`/disabled). **Trial quota is now server-accounted** (stored in `license_usage` alongside paid quota, `kind=trial`): the client/plugin should call `consume(..., kind='trial')` to deduct and treat `trialUsed`/`trialRemaining` (from `consume`/`verify`) as the trusted balance; `trialPeriodKey` is the server trial bucket key, so a new period naturally opens a new bucket → the old one resets on its own; the local count is only an offline display cache.
- **Reset rule**: resetting is fully handled by the server period bucket — when `trialPeriodKey` changes you enter a new bucket, the old one is no longer matched → the quota resets naturally, no cron needed. **Period boundaries come from the server-issued `trialPeriodKey`, never the local clock** (a rewound clock must not inflate the quota). Each period's quota is independent and never rolls over.
- **Expiry rule**: when the quota reaches zero, treat the trial as ended (guide to purchase like `expired`); `TOTAL` behaves exactly as before, and ignoring the period fields causes no errors.
- **Both at once**: a `QUOTA` product may still carry `trialDays`, so `trialCount` (quota) and `trialDays` (time) can coexist — whichever comes first ends the trial (under reset-type periods the quota refreshes each day/week/month, but the trial still ends by the `trialDays` time). Under the `EDITION` model only `trialDays` applies.

### 3.9 Usage-based quota (licensePricingModel = QUOTA / quotaAmount)

On the publish page a product can be sold either by **edition tiers** (`EDITION`, default) or by **usage quota** (`QUOTA`). A QUOTA product has a single Basic edition and sells **quota packs** (e.g. $9.9 for 20 uses, $20 for 100 uses); each pack can carry a validity period (in this mode `billingPeriod` means the **quota's valid window**). For integrators this means:

- **No deduction, no downgrade block**: quota-pack repurchases are always at full price — there is no credit-based pricing logic at all;
- **Quota is frozen onto the code**: when the platform issues the code at purchase, it writes the pack's `quotaAmount` onto **that** license code; `activate`/`verify` responses carry the field (always `null` for EDITION products, legacy codes, and trial codes);
- **How quotas accumulate = the product's upgrade strategy** (set on the publish page):
  - **Same-code upgrade (`SAME_CODE`, default)**: repurchasing on the same machine makes the platform **open a new lot** on the existing code's `license_usage` (`cap` = this pack's quota, `expires_at` = this pack's valid window); a replay of the same order won't grant a duplicate lot. Each lot expires on its own without affecting others; `quotaAmount` (display total = Σ granted lot `cap`) grows accordingly, and the spendable balance is `quotaRemaining` (Σ live lots), which the client reads directly without summing itself;
  - **New code (`NEW_CODE`, deprecated)**: as of 2026-10 this option is no longer offered on the publish/edit page and new products are always `SAME_CODE`; only legacy products keep it — each order issues an independent new code while old codes stay valid — **each code is its own wallet**; the client uses the code it currently holds (consumption is charged only against that code);
- **Read the quota from the server's lot aggregation; consumption is accounted server-side**: the platform now offers `POST /license/quota/consume` (SDK `consume(licenseCode, machineCode, activationToken, amount, requestId, kind)`, same family as `verify`, authenticated by `activationToken`, `kind` defaults to `'quota'`). Paid quota is granted as **lots** — each carries its own `cap` + `expires_at`. Report a deduction on each feature call; the server deducts from the **earliest-expiring live lot first (FIFO)** among unexpired lots with room, applying a **per-lot atomic bounded decrement** (`used + take <= cap`) and, **keyed on `licenseCode`**, shares a single balance across machines / browser instances / reinstalls — curing the multi-fold consumption where one code burns a full counter on every device. `consume` charges only the current code's lots and never touches its machine siblings. The response returns `quotaUsed` / `quotaRemaining` (= Σ live-lot `max(0, cap - used)`) as the **only trusted balance**; local counts are no longer the gating basis. **The code is never marked `expired` by quota** (exhausting or expiring all lots only drives `remaining=0` to prompt repurchase). `requestId` (8–128 chars, client-generated) is de-duplicated server-side so retries can't double-charge; an exhausted balance returns `insufficientQuota`, and a concurrent same-`requestId` request returns `quotaConsumeProcessing`. Startup `verify` now also returns `quotaUsed` / `quotaRemaining` (lagging at most one cache TTL; the immediate `consume` return is the most accurate). `license.quotaAmount` is only a display total (= Σ granted lot `cap`); if you truly need offline use, batch-report after a small grace allowance (each with its own `requestId`), accepting that the grace window may leak a few uses;
- **Don't call the upgrade endpoints for QUOTA products**: `/license/software/upgrade` and `/license/developer/upgrade` only change edition / billing period / expiry and **never touch the quota**; the platform rejects them for QUOTA products with `errorCode = quotaUpgradeUseAddQuota`. There are only two ways to add quota: send the user to the platform purchase page to repurchase (accumulates automatically), or have your server call `/license/software/addQuota` (**send `clientOrderId`** — the platform then makes the grant idempotent per order: a replay returns the first result and a concurrent duplicate gets `quotaOrderProcessing`; without it the platform cannot de-duplicate).
- **Use `trialCount` for free quota** (see 3.8), not `trialDays`; the purchase page needs no adaptation — quota packs render automatically as sub-cards inside the edition card (title = quota amount, subtitle = validity period).

### 3.10 Field × pricing-model mapping (EDITION / QUOTA)

Not every `verify` / `activate` / `consume` response field is meaningful for both pricing models. Each product picks one (product-level `licensePricingModel`); **fields not applicable to the current model are always `null`**, so render `-` defensively and never assume a field is present:

| Field | Model | Notes |
| --- | --- | --- |
| `licenseCode` / `machineCode` / `activationToken` / `status` | Common | License code / machine code / activation token / status |
| `productUniqueCode` / `source` / `maxMachines` / `activatedMachines` | Common | Product code / issue source / machine cap and bound count |
| `edition` | Common (differs in meaning) | EDITION: tier; QUOTA: always a single Basic edition (may be `null`) |
| `softwareMajorVersion` / `trialDays` / `trialExpiryTime` / `licenseDeductionEnabled` | EDITION | Major version / day-based trial / grace snapshot / upgrade proration |
| `billingPeriod` | **Dual meaning** | EDITION→subscription period (drives code `expiryTime` / renewal); QUOTA→per-lot validity period (per-lot `expires_at`) |
| `quotaAmount` / `quotaUsed` / `quotaRemaining` / `quotaNextExpiry` | QUOTA | Display total / used / remaining / quota expiry; **`quotaAmount` is always `null` for EDITION** |
| `trialCount` / `trialCountPeriod` / `trialPeriodKey` / `trialUsed` / `trialRemaining` | QUOTA | Per-use trial quota / period / bucket key / used / remaining; **always `null` for EDITION** (the trial dimension is mutually exclusive) |
| `consume` (`kind: 'quota' \| 'trial'`) | QUOTA | Quota-consumption endpoint; EDITION never calls it |

> Key points: `billingPeriod` is dual-meaning (EDITION = subscription period, QUOTA = per-lot validity; their products never interact). Gate on `quotaRemaining` only (`consume`'s immediate return is freshest; `verify` lags at most one cache TTL); read quota expiry from `quotaNextExpiry` (when `null`, infer "perpetual" / "used up" off `quotaRemaining`). EDITION products touch none of the quota fields.

## 4. Scenario B: orders off-platform

### 4.1 Prerequisites

1. Publish the product on PowerSoftware with licensing enabled (`licenseEnabled = true`)
2. Get `licenseApiSecret` from the developer console (**server-side only, never leak to the client**)

### 4.2 Architecture

```
Client                         Your backend                     PowerSoftware platform
  │                              │                              │
  │  user pays (your channel)    │                              │
```

```python
server_client = LicenseClient(

def issue_license(user_machine_code, edition="PRO", order_id=""):

        expiry_days=365,
```

## 5. SDK method cheat-sheet

| Method | Scenario A | Scenario B | Signed | Notes |
|---|:---:|:---:|:---:|---|
| `machine_code()` | ✅ | ✅ | — | Generate machine code (consistent across languages) |
| `claim_trial(mc)` | ✅ | — | — | Claim a trial license (trial-first products only) |
| `activate(code, mc)` | ✅ | ✅ | — | Activate a code, bind the machine |
| `verify(code, mc, token)` | ✅ | ✅ | — | Verify license state |
| `verify_cached(code, mc, token)` | ✅ | ✅ | — | Verify with a 60s local cache |
| `consume(code, mc, token, amount, requestId, kind)` | ✅ | ✅ | — | Server-side quota consumption (QUOTA only; `kind`=`quota`/`trial`; returns `quotaRemaining`/`trialRemaining`) |
| `deactivate(code, mc)` | ✅ | ✅ | — | Unbind a machine (requires login; browser scenarios) |
| `purchase_url(mc)` | ✅ | — | — | Build the platform purchase URL |
| `check_update(currentVersion)` | ✅ | ✅ | — | Check for updates; returns latest version and whether an update exists |
| `generate_for_software(mc, edition, ...)` | — | ✅ | HMAC | In-app issuance (backend only) |
| `upgrade_for_software(code, edition, ...)` | — | ✅ | HMAC | In-app upgrade/renewal (backend only) |

> **Response fields**: `activate`/`verify`/`claim_trial` also return `licenseUpgradeMode` (`SAME_CODE` keeps the code / `NEW_CODE` re-binds a new one; `NEW_CODE` was deprecated in 2026-10 — new products are always `SAME_CODE`, and the field is still returned for legacy compatibility). Clients use it to decide whether to show a "bind license code" input: with `SAME_CODE` the code never changes so don't prompt for re-entry; with `NEW_CODE` overwrite local storage with the code returned by `software/upgrade`. Defaults to `SAME_CODE` when unset.
>
> The same three calls also return `trialExpiryTime` (original trial expiry, non-`null` after trial-to-purchase) for the grace-period feature — see §3.6.
>
> They also return `trialCount` (edition trial-quota config, the grant `cap` template, `null` when disabled; **now server-accounted in period buckets**, decremented via `consume(kind='trial')`, returning `trialUsed`/`trialRemaining`), plus `trialCountPeriod` (`TOTAL`/`DAILY`/`WEEKLY`/`MONTHLY`) and `trialPeriodKey` (server period key when reset-type — the server trial bucket key) — see §3.8.

### 5.1 Check for updates (checkUpdate)

```python
result = client.check_update("1.2.0")
# returns { "hasUpdate": True, "latestVersion": "1.3.0" }
# returns { "hasUpdate": False, "latestVersion": None } when the product is missing/unlisted/has no version
```

```javascript
const result = await client.checkUpdate('1.2.0');
// { hasUpdate: true, latestVersion: '1.3.0' }
```

```java
Map<String, Object> result = client.checkUpdate("1.2.0");
```

Integration tips:

- **When to call**: asynchronously at startup, then at most once every ≥ 6 hours. The server caches aggressively, so a single request is very cheap.
- **Prompt upgrade**: when `hasUpdate=true`, show `latestVersion` and guide the user to the product detail page to download (build its URL from the same base as `purchase_url(mc)`, or from the publish page).
- **Silent degrade**: catch and skip on any network/other error — never block the main flow.

```python
def check_update_quietly(client, current_version):
    try:
        return client.check_update(current_version)
    except Exception:
        return {"hasUpdate": False, "latestVersion": None}  # silent degrade on network errors
```

## 6. Local credential storage

The SDK does not persist anything; you implement it. What to store:

```json
{
  "licenseCode": "XXXXXXXXXXXX",
  "activationToken": "YYYYYYYYYYYY",
  "lastVerify": {
    "valid": true,
    "edition": "ULTIMATE",
    "expiryTime": 1735689600000,
    "trialExpiryTime": 1735000000000,
    "cachedAt": 1735689600000
  }
}
```

**Principles:**
- Store only `licenseCode` + `activationToken` + the last verify result
- Do not store decryptable full license info (defeating reverse engineering is pointless; it's only a cache)
- `verifyCached`'s 60s cache lives in the SDK process and is lost on restart, so `verify` must be called again

## 7. Edition-level comparison

Developers define edition codes (e.g. `BASIC`/`PRO`/`ULTIMATE`) on the publish page. Any product form with licensing enabled can define custom editions. Clients compare by level:

```python
# TRIAL license = all features; give it the highest level
# (omitting TRIAL would leave only basic features during the trial!)
EDITION_LEVEL = {"BASIC": 0, "PRO": 1, "ULTIMATE": 2, "TRIAL": 99}

def edition_sufficient(user_edition, required_edition):
    return EDITION_LEVEL.get(user_edition, 0) >= EDITION_LEVEL.get(required_edition, 0)
```

Common mapping (reference):

| Tier | edition code | Level | Typical features |
|---|---|---|---|
| Basic | `BASIC` | 0 | Basic editing, format conversion |
| Pro | `PRO` | 1 | Batch processing, HD upscaling |
| Ultimate | `ULTIMATE` | 2 | AI repair, cover assistant |
| Trial | `TRIAL` | 99 (all) | Platform-issued trial license, exclusive to trial-first products |

> Edition names/codes are customized by developers on the platform; they need not be BASIC/PRO/ULTIMATE. Prices and feature lists appear on the purchase page only when "platform-collected license fee" is checked. See §3.6 for trial-to-purchase higher-tier grace.

## 8. Error-code handling

The SDK throws `LicenseError` with an `error_code` attribute:

```python
from ps_license_sdk import LicenseError

try:
    result = client.verify_cached(...)
except LicenseError as e:
    if e.error_code == "expired":
        open_purchase_page()
    elif e.error_code == "revoked":
        show_message("License revoked, please contact support")
    elif e.error_code == "machineLimit":
        show_message("Machine limit reached, unbind an old device in your profile")
    elif e.error_code == "NETWORK_ERROR":
        show_message("Network error, check your connection and retry")
    else:
        show_message(f"Verification failed: {e}")
```

| Error code | Meaning | Suggested client handling |
|---|---|---|
| `codeNotFound` | License code not found | Check input |
| `revoked` | Revoked | Contact support |
| `expired` | Expired | Guide to purchase/renew |
| `machineLimit` | Machine limit reached | Guide to unbind in profile |
| `tooManyAttempts` | Rate limited | Retry later |
| `trialNotEnabled` | Trial not enabled for the product | Check platform config |
| `trialAlreadyPurchased` | Already purchased (trial claim blocked) | Prompt already-owned, guide to activate/verify existing code |
| `quotaUpgradeUseAddQuota` | Upgrade endpoint called on a QUOTA product | Repurchase or use `addQuota` to extend quota |
| `quotaOrderProcessing` | Concurrent addQuota for the same `clientOrderId` | Retry later; don't re-send under a new order id |
| `insufficientQuota` | `consume` hit an exhausted server balance | Send the user to repurchase / `addQuota` |
| `quotaConsumeProcessing` | Concurrent consume for the same `requestId` | Retry later with the **same** `requestId` |
| `NETWORK_ERROR` | Network/timeout | Offline grace or retry |

## 9. Purchase-page redirect & site selection

### 9.1 Purchase URL

```text
https://www.powersoftware.app/product/license/purchase?productUniqueCode={productUniqueCode}&machineCode={machineCode}
```

SDK methods:

```python
url = client.purchase_url(mc)
url = client.purchase_url(mc, base="https://www.powersoftware.cn")
```

### 9.2 Which site: `.app` (global) vs `.cn` (China)

| | `powersoftware.app` (global) | `powersoftware.cn` (China) |
|---|---|---|
| Payment | Alipay + PayPal | Alipay only |
| Country/currency | Cloudflare geo by IP (CN→CNY, else→USD) | Fixed `country=CN`, CNY |
| Language | By URL prefix / `Accept-Language` | Fixed `zh-CN` |
| For whom | International / overseas users | Mainland China users |

**The SDK defaults to `.app` and does not auto-detect.** The client decides which `base` to pass.

#### How to decide

**Option 1: by system language (recommended)**

```python
import locale

def get_purchase_base():
    sys_lang = locale.getdefaultlocale()[0] or ""
    if sys_lang.startswith("zh"):
        return "https://www.powersoftware.cn"
    return "https://www.powersoftware.app"
```

```javascript
function getPurchaseBase() {
    const lang = process.env.LANG || "";
    return lang.toLowerCase().startsWith("zh")
        ? "https://www.powersoftware.cn"
        : "https://www.powersoftware.app";
}
```

```java
String getPurchaseBase() {
    return "zh".equals(Locale.getDefault().getLanguage())
        ? "https://www.powersoftware.cn"
        : "https://www.powersoftware.app";
}
```

**Option 2: a user setting** — offer a "region" option in settings.

**Option 3: hardcode** — for China-only software, just set `base="https://www.powersoftware.cn"`.
