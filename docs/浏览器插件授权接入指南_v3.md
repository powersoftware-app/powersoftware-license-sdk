# 浏览器插件授权接入指南（v3）

> 适用于：以浏览器插件（Chrome Extension / Edge Add-on / Firefox Add-on，MV3）形态发布产品，集成授权 SDK 实现版本控制与付费功能拦截。
> 关联文档：[客户端软件授权接入指南](客户端软件授权接入指南_v3.md) ｜ [授权 SDK 规范](授权SDK规范_v3.md)

## 一、为什么插件拿不到机器码

浏览器沙箱环境下，插件代码拿不到任何硬件标识：

| 标识 | 客户端软件（SDK `machineCode()`） | 浏览器插件 |
|---|---|---|
| BIOS 序列号 / MachineGuid / MAC | ✅ 可采集 | ❌ 沙箱禁止 |
| 硬件指纹（跨重装稳定） | ✅ 同一台机器永远同码 | ❌ 无对应能力 |
| 稳定标识 | 硬件指纹 + 本地持久化 UUID | 只能自生成 Install ID |

因此插件的「机器码」**降级为插件 Install ID**：`EXT-` 前缀 + 随机 UUID，首次启动生成后持久化。服务端按 `EXT-` 前缀自动识别为插件类型（`user_machine.machine_type = PLUGIN`），激活/校验/购买跳转链路与客户端软件**完全一致**，无需任何服务端适配。

## 二、SDK 安装

拷贝单文件 `node/src/webextension.js` 到你的插件项目中，零依赖、可直接打包（不依赖任何 node 模块，签名用 Web Crypto 实现）：

```
node/src/
├── index.js         桌面/服务端客户端 SDK（硬件指纹机器码）
└── webextension.js  浏览器插件适配层（EXT- Install ID）← 插件项目用这个
```

manifest.json 需声明 `storage` 权限：

```json
{
  "manifest_version": 3,
  "permissions": ["storage"]
}
```

> `webextension.js` 复用了 `index.js` 中 `LicenseClient` 的全部接口签名，仅两处不同：`machineCode()` 变为**异步**；`sign()` 为异步（内部使用，接入方一般无需感知）。

## 三、核心代码

```js
// background.js（MV3 service worker）
import { LicenseClient, machineCode, deviceId } from './webextension.js';

const client = new LicenseClient({ productUniqueCode: 'PRO-2026-001' });

// ---------- 首次启动：领取试用 ----------
async function claimTrial() {
  const mc = await machineCode();                       // 异步，返回 EXT-xxxxxxxx-...
  const did = await deviceId();                          // 异步，返回 DID-xxxxxxxx-...（试用防刷，见 3.4）
  const result = await client.claimTrial(mc, did);       // did 作 x-device-id 头上报；缺省/非法视同未上报
  await saveCred({ licenseCode: result.licenseCode, activationToken: result.activationToken });
}

// ---------- 点击付费功能时校验（60s 缓存） ----------
async function checkLicense(requiredEdition = 'PRO') {
  const cred = await loadCred();
  if (!cred?.licenseCode) return { valid: false, reason: '未激活' };
  try {
    const mc = await machineCode();
    const result = await client.verifyCached(cred.licenseCode, mc, cred.activationToken);
    if (!result.valid) return { valid: false, reason: '授权无效或已过期' };
    const levels = { BASIC: 0, PRO: 1, ULTIMATE: 2, TRIAL: 99 };
    if ((levels[result.edition] ?? 0) < levels[requiredEdition]) {
      return { valid: false, reason: `需要 ${requiredEdition} 及以上版本` };
    }
    return { valid: true, edition: result.edition, expiryTime: result.expiryTime };
  } catch (e) {
    if (e.errorCode === 'machineLimit') return { valid: false, reason: 'machineLimit' };
    return { valid: false, reason: String(e) };
  }
}

// ---------- 用户购买后输入授权码激活 ----------
async function activate(licenseCode) {
  const mc = await machineCode();
  const result = await client.activate(licenseCode, mc);
  await saveCred({ licenseCode, activationToken: result.activationToken });
}

// ---------- 购买页跳转（自动携带 EXT- 机器码，下单即绑到买家名下） ----------
function openPurchasePage(mc) {
  chrome.tabs.create({ url: client.purchaseUrl(mc) });
}
```

本地凭证持久化规范与客户端软件一致（只存 `licenseCode` + `activationToken` + 最近一次 verify 结果），但**存储位置不同**，见下节。

### 3.1 试用额度（trialCount / trialCountPeriod）

插件形态的试用维度与客户端软件同口径：平台**不再按插件形态预置默认额度**，需在发布页显式配置试用额度（`TRIAL_FIRST` + 按量额度包 `QUOTA` 且未配置时，平台兜底默认 20；试用天数可为 0），与时间试用并存为「按额度试用」的第二套模式：

- `claimTrial` / `activate` / `verify` 的成功响应均返回 `trialCount`（产品级配置值；未启用为 `null`），并附带 `trialCountPeriod`（`TOTAL` 累计，默认，与存量行为一致 / `DAILY` 每日 / `WEEKLY` 每周（ISO-8601 自然周）/ `MONTHLY` 每自然月重置）与 `trialPeriodKey`（仅重置型周期下发，服务器当前周期 key，如 `DAILY="2026-09-30"`、`WEEKLY="2026-W39"`、`MONTHLY="2026-09"`）；
- **试用额度已纳入服务端记账**（与付费额度同存 `license_usage`，`kind=trial`）：每次试用功能调用改调 `consume(..., kind='trial')` 扣减，以响应回带的 `trialUsed` / `trialRemaining` 为唯一可信余额；插件本地计数（`chrome.storage.local`）仅作离线展示缓存，不再作为拦截依据——本地记账拦不住多设备/重装刷额度，见 3.2；
- **重置交给服务端周期桶**：`trialPeriodKey` 即服务端试用桶 `bucket_key`，新周期自然落新桶 → 旧桶不再命中 → 额度天然清零，插件无需任何定时任务；下一次重置时刻直接读响应 `trialNextResetTime` 展示，**勿用 `Date.now()` 自行判定周期**（防改本地时钟提前重置）；每周期额度不结转；
- 额度归零即视为试用结束，按 `expired` 同等体验处理（引导购买）；
- 产品级配置、与计费周期无关（不同周期不累加）；与时间试用（`trialDays`）同时配置时，任一先到即试用结束；
- **按量额度产品（`licensePricingModel = QUOTA`）**：若产品发布页选的是按量额度售卖，购买后 `activate` / `verify` 响应额外返回两个额度字段：`quotaAmount`（**这一张码**的额度，`SAME_CODE` 策略下同机复购已在原码累加）与 `quotaTotal`（**同一机器码上该产品全部有效码的额度求和**）。**可用总额度请优先取 `quotaTotal`**：累加只在「`SAME_CODE` + 下单带了机器码 + 该机已持有同版本有效码」时命中，其余情形（`NEW_CODE`、从网页直接下单未带机器码、换机复购）会另发一张独立新码，只看单张 `quotaAmount` 就会「付两包只见一包」；旧版缓存条目没有 `quotaTotal` 时回退旧口径（`SAME_CODE` 取 `quotaAmount`，`NEW_CODE` 自行把同机多码求和）。**付费额度（`quotaAmount`/`quotaTotal`）的消耗请改调平台 `POST /license/quota/consume`（SDK 方法 `consume(...)`）做服务端记账**，以响应回带的机器级 `quotaRemaining` 作为唯一可信余额（见 3.2）；`trialCount` 免费试用额度同为服务端记账，扣减走 `consume(..., kind='trial')`。详见《客户端软件授权接入指南》3.8 节（试用额度）、3.9 节（按量额度产品）。

### 3.2 多浏览器 / 多笔记本共用一个码：本地记账拦不住多倍消耗（重要）

插件拿不到硬件机器码，只能用 Install ID 当 `machineCode`，而用量记在 `chrome.storage.local`。同一张授权码因此会在**每台设备/每个浏览器实例上各自持有一份完整用量**：

| 现象 | 成因 | 后果 |
|---|---|---|
| 家里 + 公司各买 100 次，两处都能用满 100 | 本地各存一份 `used`，互不可见 | 卖 100 次实付 100，实际消耗 200 |
| 重装插件 / 清浏览数据后额度“满血复活” | `storage.local` 被清空，`used` 归零 | 反复重置可免费刷额度 |
| 手工改存储即可无限额度 | 插件侧无任何可信执行环境 | 本地记账不可作为收费依据 |

平台此前的约束只能**限制机器数**（`maxMachines`），不能限制**消耗速率**：本码 `quotaAmount` 回答“这张码买了多少”，不回答“已经花了多少”。**现在平台已上线消耗记账接口 `POST /license/quota/consume`（SDK 方法 `consume(...)`，与 `verify` 同族、凭 `activationToken`），把“已经花了多少”从本地抬到服务端**，直接拦住多倍消耗：

- 用量落在服务端 `license_usage` 分票/分桶表上，**以 `licenseCode`（不是 Install ID）为记账主键**，同一张码跨浏览器/跨笔记本/重装共享同一份账，扣完即止；重装或清浏览数据不再“刷新额度”；付费额度按“票(lot)”发放（每票自带 `cap` + 各自有效期 `expires_at`），消耗在未过期且有剩的票里**最早到期先扣（FIFO）**，`quotaRemaining = Σ 有效票 (cap - used)`；**授权码不因额度耗尽/全部过期而 expired**（只让 remaining=0 引导复购）；
- 插件每次功能调用改调 `consume(licenseCode, machineCode, activationToken, amount, requestId, kind)`（`amount` 为正数，支持小数，如按 token/时长计费可传 `0.5`；`kind` 默认 `'quota'`；试用额度传 `'trial'` 走服务端周期桶记账），服务端在选中的票上**逐票原子有界扣减**（`used + take <= cap` 且票未过期，只扣当前这张码的票、不动同机兄弟码），并回带票聚合的 `quotaRemaining`（或 `trialRemaining`）作**唯一可信余额**；本地 `used` 只当离线展示缓存，不再作为拦截依据；
- 幂等：`requestId`（8–128 位，客户端生成；复合键请先定长哈希）由服务端去重，防止重试双扣；同一 `requestId` 并发处理中返回 `quotaConsumeProcessing`，额度不足返回 `insufficientQuota`；
- 余额对齐：启动 `verify` 现回带本码 `quotaUsed` / `quotaRemaining`（含试用侧 `trialUsed` / `trialRemaining`，最长滞后一个缓存 TTL），据此校准本地展示；以 `consume` 的即时返回值为最准确余额；
- 离线/弱网：允许插件本地小额宽限（如 ≤ 5 次）后批量补报（每次带各自 `requestId`），接受“宽限窗口内可能被多花几次”的残余风险；额度用尽后须联网 `consume` 成功才继续。

试用额度（`trialCount`）同样走服务端周期桶记账（`consume(..., kind='trial')`），见 3.1。

### 3.2.1 计费权威上移到你的服务端 / 网关（有服务端能力时更稳）

3.2 的服务端记账把「花了多少」抬到了服务端,但**调 `consume` 的仍是插件自己**——这依然是一个**可伪造的客户端信号**:反编译或抓包拿到 `licenseCode + machineCode + activationToken` 三元组的人,可以**根本不调 `consume` 直接打付费功能**,服务端余额纹丝不动(即 §3.2「边界」所述:功能不依赖回包就拦不住)。

**若你的产品本身有一跳服务端能力**(AI 推理、云资源中转等——功能真需要回包才成立),更稳的接法是把扣费落账**放到你自己的服务端 / 网关**:由服务端在资源**真正消耗之后**调 2.8 `consume`(同一套三元组鉴权 + 自持 `requestId` 幂等,重试不双扣),客户端因此**不再需要持有任何计费真相**。此时:

- 客户端只保留一份**余额镜像 + 软门禁**:它不发请求就能挡住「已确认耗尽」的用户(省一次往返、省一笔已烧的资源),权威余额仍以 `verify` / `consume` 回包为准;
- 消耗明细(订阅卡 / 用量页的「最近消耗」)改读 2.9 `/license/quota/txn`,不再本地自算累计;
- `consume` 的 `requestId` 幂等意味着将来可把多笔明细**合并成一次落账**(攒批),契约与客户端都不动。

> 反之,没有服务端中转的纯本地功能,只能沿用 3.2 的「客户端调 consume」模型,并接受「不调就拦不住」的残余风险——此时服务端记账的价值是提高作弊成本 + 留证据,而非密码学不可破。

### 3.3 字段与计费模型对照（EDITION / QUOTA）

`verify` / `activate` / `consume` 响应字段并非对两种计费模型都有意义。产品二选一（产品级 `licensePricingModel`），**不适用于当前模型的字段恒为 `null`**，插件应统一容错显示 `-`：

| 字段 | 适用模型 | 说明 |
| --- | --- | --- |
| `licenseCode` / `machineCode` / `activationToken` / `status` | 通用 | 授权码 / 机器码（插件为 Install ID）/ 激活凭证 / 状态 |
| `productUniqueCode` / `source` / `maxMachines` / `activatedMachines` | 通用 | 产品编码 / 来源 / 机器数上限与已绑 |
| `edition` | 通用（语义不同） | EDITION 为档位；QUOTA 恒单一基本版（可 `null`） |
| `softwareMajorVersion` / `trialDays` / `trialExpiryTime` / `licenseDeductionEnabled` | EDITION | 大版本 / 按天试用 / 宽限快照 / 升级补差价 |
| `billingPeriod` | **双语义** | EDITION→订阅周期（驱动码 `expiryTime`/续费）；QUOTA→每张额度票的有效期周期（逐票 `expires_at`） |
| `quotaAmount` / `quotaUsed` / `quotaRemaining` / `quotaNextExpiry` | QUOTA | 展示总额 / 已用 / 剩余 / 额度有效期；**`quotaAmount` 对 EDITION 恒 `null`** |
| `trialCount` / `trialCountPeriod` / `trialPeriodKey` / `trialUsed` / `trialRemaining` / `trialNextResetTime` | QUOTA | 按次试用额度 / 周期 / 桶 key / 已用 / 剩余 / 下次重置时间；**对 EDITION 恒 `null`** |
| `consume`（`kind: 'quota' \| 'trial'`） | QUOTA | 额度消耗接口；EDITION 不调用 |

> 重点：`billingPeriod` 双语义；额度门禁只读 `quotaRemaining`（`consume` 即时返回最准，`verify` 最长滞后一个缓存 TTL），额度有效期读 `quotaNextExpiry`（`null` 时按 `quotaRemaining` 判「永久」/「已用尽」）。

### 3.4 设备标识 `x-device-id`（试用防刷，建议上报）

试用领取（`claimTrial`）服务端会做设备 + 网段的防刷审查。**建议**带上可选请求头 `x-device-id`：不报不会报错，但服务端只能退回按网段维度判定，上报缺失/异常时本次发放可能被缩短。

**为什么不能直接拿 Install ID（`machineCode`）当设备标识**：`machineCode`（`EXT-` Install ID）走 `storage.sync` **跟随 Chrome 账号**，家里/公司会拿到同一个 ID——它表达的是「这个人的浏览器身份」；而设备闸门要区分「多机各一装」，需要一个**绑物理浏览器**、不跨设备同步的标识。两者各司其职。

**默认生成方式（SDK `deviceId()`）**：首次生成 `DID-` + `crypto.randomUUID()`，仅持久化到 `chrome.storage.local` 的 `psDeviceId`（**不写 sync**，避免复制到其它设备误触防刷）；格式恒为 `DID-<uuid>`，与服务端白名单正则 `^DID-[A-Za-z0-9_-]{6,64}$` 一致。清除浏览器数据会重置（视同新设备，可接受）：

```js
import { deviceId } from './webextension.js';
const did = await deviceId();            // DID-xxxxxxxx-xxxx-...
await client.claimTrial(mc, did);        // SDK 内部将 did 放进 x-device-id 请求头
```

**可选加强：活过卸载**（与官方插件的 `ps_did` 第一方 cookie 同效）：`storage.local` 会随卸载清空；若希望设备标识在卸载重装后仍保持不变，改在 API 域写一个第一方 cookie（cookie 存浏览器 profile，卸载插件不清）。需在 manifest 额外声明 `cookies` 权限与 `host_permissions`：

```json
{
  "manifest_version": 3,
  "permissions": ["storage", "cookies"],
  "host_permissions": ["https://www.powersoftware.app/*"]
}
```

```js
// 先试读 ps_did cookie，没有则生成 DID-<uuid> 并写入（expiration 设长，活过卸载）
async function deviceIdViaCookie(url = 'https://www.powersoftware.app') {
  const existing = await chrome.cookies.get({ url, name: 'ps_did' });
  if (existing?.value && /^DID-[A-Za-z0-9_-]{6,64}$/.test(existing.value)) return existing.value;
  const did = 'DID-' + crypto.randomUUID();
  await chrome.cookies.set({ url, name: 'ps_did', value: did, expirationDate: Date.now() / 1000 + 60 * 60 * 24 * 365 * 5 });
  return did;
}
```

> 两种方式二选一即可：普通接入直接用 SDK `deviceId()`；要跨卸载稳定再用 cookie 加强版。无论哪种，最终都作为 `claimTrial(mc, did)` 第 2 参传入，由 SDK 放 `x-device-id` 头。

## 四、Install ID 的持久化策略

`machineCode()` 内部已完成双写，接入方无需处理，但需要理解其行为：

| 存储 | 作用 | 何时丢失 |
|---|---|---|
| `chrome.storage.local` | 保底，本浏览器实例内稳定 | 卸载插件 / 清除浏览器数据 |
| `chrome.storage.sync` | 跟随用户 Chrome 账号，**跨设备同 ID** | 用户退出账号并清除同步数据 |

读取优先级：`sync → local → 新生成`；两者冲突时以 `sync` 为准（跟随账号）。

**实际效果**：用户登录了 Chrome 账号时，家里/公司电脑、重装浏览器后 Install ID 都不变，等于免费把「浏览器实例」升级为「这个人的 Chrome 身份」。

## 五、删除插件后重新安装怎么处理（重点）

### 5.1 三个场景

| 场景 | Install ID | 本地凭证（licenseCode/token） | 用户感知 |
|---|---|---|---|
| 重装插件，**登录了 Chrome 账号** | ✅ 不变（sync 恢复） | ❌ 丢失（凭证只存 local） | 需重新激活一次 |
| 重装插件，**未登录账号** | ❌ 变为新 ID | ❌ 丢失 | 需重新激活，可能触发机器数上限 |
| 只清除浏览数据，插件还在 | ❌ local 丢失，sync 有则不变 | ❌ 丢失 | 同上 |

**结论：无论如何设计，重装后本地凭证都会丢。问题的本质不是「识别不到同一台机器」，而是「识别不到同一个用户」——解法是把身份锚点放在授权码/账号上，而不是设备上。**

### 5.2 推荐方案：licenseCode 冗余存入 storage.sync

把授权码（非密钥）也同步到 `storage.sync`，重装后即可**自动恢复激活，用户零输入**：

```js
const CRED_KEY = 'psLicenseCred';

async function saveCred(cred) {
  // token + licenseCode 双写 local 与 sync
  await chrome.storage.local.set({ [CRED_KEY]: cred });
  await chrome.storage.sync.set({ [CRED_KEY]: cred }).catch(() => {});
}

async function loadCred() {
  const local = (await chrome.storage.local.get([CRED_KEY]))[CRED_KEY];
  if (local) return local;
  // 重装/清数据后：从 sync 恢复
  const synced = (await chrome.storage.sync.get([CRED_KEY]))[CRED_KEY];
  if (synced) {
    await chrome.storage.local.set({ [CRED_KEY]: synced });
    return synced;
  }
  return null;
}
```

重装后的启动流程：

```
插件启动
  │
  ├─ loadCred() 从 sync 恢复了 licenseCode？
  │     ├─ 是 → activate(licenseCode, 新 Install ID) 静默重新绑定
  │     │        ├─ 成功 → 恢复激活，用户无感知
  │     │        └─ machineLimit → 走 5.3 解绑引导
  │     │
  │     └─ 否 → 展示激活页：输入授权码 / 跳转购买页
  │
  └─ verifyCached 通过 → 正常使用
```

> **注意**：静默重新激活要求授权码的机器绑定数有余量（新 Install ID ≠ 旧 ID 的场景，即用户未登录 Chrome 账号时）。登录了账号的用户 ID 不变，直接通过。

### 5.3 machineLimit：绑定数已满

未登录账号的用户反复重装会产生多个 `EXT-` ID，当授权码绑定的机器数达到 `maxMachines` 时，`activate` / `verify` 返回 `machineLimit` 错误码。客户端按既定文案处理即可：

```js
if (result.valid === false && result.reason === 'machineLimit') {
  showPage(`
    已达设备绑定上限。
    ① 打开个人中心，解绑不再使用的设备后重试；
    ② 若刚重装过插件且登录了 Chrome 账号，重新登录后 Install ID 会自动恢复。
  `);
}
```

解绑途径（与客户端软件共用）：

- **个人中心**：用户自助解绑旧设备；
- **SDK `deactivate(code, mc)`**：在插件设置页提供「解绑本设备」按钮（需登录态）；
- **换绑配额**：自助解绑后 30 天内不可再次解绑（平台侧限制，防止恶意换绑），错误码 `unbindQuotaExceeded`。

### 5.4 平台侧如何看「插件机器码」

- 服务端按 `EXT-` 前缀自动归类 `machineType=PLUGIN`，后台机器码分页支持按类型筛选；
- 运营排查用户问题时：插件用户的「一台设备」= 一个浏览器实例（未登录账号）或一个 Chrome 账号（登录账号），与「物理电脑」不是一回事，解释话术需注意；
- 风控：同一授权码在短时间内频繁出现**新的** `EXT-` ID 激活，通常是未登录账号反复重装或恶意共享，可人工核实后调整绑定数。

## 六、错误码处理

与客户端软件完全一致（`codeNotFound` / `revoked` / `expired` / `machineLimit` / `tooManyAttempts` / `trialNotEnabled` / `trialAlreadyPurchased` / `NETWORK_ERROR`），处理方式参见 [客户端软件授权接入指南 · 错误码](客户端软件授权接入指南_v3.md#八错误码处理)。插件场景需额外注意：

- MV3 service worker 随时休眠，**60s verify 缓存随 worker 生命周期失效**，属正常现象，无需处理；
- `NETWORK_ERROR` 时建议离线放行最近一次 verify 结果（可自行加时间窗，如 72h 宽限）。
