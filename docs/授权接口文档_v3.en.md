# License Open-API Reference v3

This document stays aligned with the platform backend (`ps-frontend-service` / `ps-worker-dependency`) and covers every open endpoint a client-software integration needs. The Node / Python / Java SDKs wrap these endpoints; the mapping is at the end.

---

## 1. Conventions

### 1.1 Base URL

```text
https://www.powersoftware.app/frontApi
```

All endpoints are `POST` with `Content-Type: application/json`.

### 1.2 Response envelope

Every endpoint returns a uniform structure:

```json
{
  "success": true,
  "code": "SUCCESS",
  "requestId": "req-xxxx",
  "content": { ... }
}
```

| Field | Type | Description |
| --- | --- | --- |
| success | boolean | `true` business success, `false` failure |
| code | string | `SUCCESS` on success; `BUSINESS_WARNING` (business failure) / `PARAM_VALIDATE_FAILED` (validation) / `SYSTEM_ERROR` on failure |
| requestId | string | Request trace ID, include it when reporting issues |
| content | object | Business payload, meaningful only when `success=true` |
| tip | string | Localized error hint (per request `Accept-Language`) |
| errorMessage | string | Business error code, e.g. `LICENSE.error.codeNotFound`, for programmatic branching |

The SDK unwraps this envelope: on success it returns `content` directly, on failure it throws (the `errorCode` is the `code` field).

### 1.3 Core terms

| Term | Field | Description |
| --- | --- | --- |
| License code | `licenseCode` | Unique code generated by the platform; Sandbox test codes are prefixed `T-` |
| Machine code | `machineCode` | Client-generated device ID, ≥ 8 chars; the three SDK languages share one algorithm (`M` + first 32 chars of Base64URL(SHA-256)) |
| Activation token | `activationToken` | HMAC credential issued by the platform on activate/issue; stored locally, sent back on verification |
| Edition | `edition` | Edition identifier (e.g. BASIC / PRO / ULTIMATE / TRIAL) |
| Expiry | `expiryTime` | ISO8601 string, `null` = perpetual |
| Trial-expiry snapshot | `trialExpiryTime` | Non-`null` after trial-to-purchase; clients use it to decide higher-tier grace |
| Upgrade policy | `licenseUpgradeMode` | `SAME_CODE` (upgrade keeps the code) / `NEW_CODE` (revoke old, issue new); `NEW_CODE` was deprecated in 2026-10 — no longer offered on the publish/edit page, new products are always `SAME_CODE`, and the field is still returned for legacy compatibility |
| Trial quota | `trialCount` | Product-level config (the grant `cap` template); the platform accounts it in server period buckets (`kind=trial`), decremented by §2.8 `quota/consume` |
| Trial-quota period | `trialCountPeriod` | `TOTAL` (cumulative, default, ends when used up) / `DAILY` / `WEEKLY` (ISO-8601 week) / `MONTHLY` (reset each calendar day/week/month); determines the server trial bucket key |
| Trial period key | `trialPeriodKey` | Server current period key for reset-type periods (`DAILY`=`"2026-09-30"`, `WEEKLY`=`"2026-W39"`, `MONTHLY`=`"2026-09"`), i.e. the server trial bucket `bucket_key`; a new period opens a new bucket → the old one resets on its own (`TOTAL`/disabled → `'ALL'` cumulative bucket) |
| Trial next reset time | `trialNextResetTime` | Trial quota "next reset time" (a UTC boundary derived into the response): for reset-type periods it returns when the current trial bucket rolls into the next segment (DAILY→next day 00:00 / WEEKLY→next Monday 00:00 / MONTHLY→1st of next month 00:00), i.e. the moment the server trial bucket key changes and the balance naturally resets; `null` for `TOTAL`/disabled/EDITION; the trial-side counterpart of `quotaNextExpiry` |
| Billing period | `billingPeriod` | `PERMANENT` / `MONTHLY` / `YEARLY`; frozen onto the license at purchase/upgrade time and returned by all license responses; legacy and trial codes fall back to `PERMANENT`; also usable as a request param in §2.6 to pick the target period |
| License pricing model | `licensePricingModel` | Product-level config: `EDITION` (feature tiers, default, supports proration on upgrade) / `QUOTA` (usage-based, sells quota packs); drives purchase and quota semantics |
| Quota amount | `quotaAmount` | The display total for **this one license code** (= Σ granted lot `cap`), frozen at purchase; returned by `verify` / `activate`; the authoritative spendable balance is the lot-aggregated `quotaRemaining`; `null` for EDITION, legacy and trial codes |
| Used quota | `quotaUsed` | QUOTA products only: this code's **server-side accumulated used over live lots** (`license_usage` per-lot (kind, bucket_key) ledger, FIFO-decremented by §2.8 `quota/consume`), shared across devices/reinstalls for one code; `null` for EDITION |
| Remaining quota | `quotaRemaining` | QUOTA products only: Σ live-lot `max(0, cap - used)` (expired lots drop out entirely), this code's remaining; the client gates on it and routes to purchase at zero (`consume`'s immediate return is freshest; `verify` lags at most one cache TTL); no longer `quotaAmount - quotaUsed` |
| Quota expiry | `quotaNextExpiry` | QUOTA products only: the earliest `expires_at` among unexpired paid lots that still have remaining (`expires_at` ISO8601); `null` when a perpetual lot still has remaining or no lot has remaining (the client renders "perpetual" / "used up" off `quotaRemaining`); returned by `verify` / `activate` / `consume`; `null` for EDITION |
| Software issue secret | `licenseApiSecret` | Auto-generated when a product enables "license activation"; stored on the software's server only, never in the client |

> Note: `billingPeriod` is stored on the license record (frozen at purchase/upgrade/renewal); `verify` / `activate` / `trial/claim` / `software/generate` / `software/upgrade` all return it so clients can render a "monthly/yearly" badge. Legacy and trial codes are `PERMANENT`.

> Usage quota (`licensePricingModel = QUOTA`): the product sells **quota packs** (e.g. 20 / 100 uses, each optionally with a validity window — `billingPeriod` then means "quota validity"), and the pack's `quotaAmount` is frozen onto the license at purchase. The platform applies no proration and blocks no downgrade. How quotas accumulate depends on the product's upgrade mode: ① `SAME_CODE` (keep original code, default) — a repurchase on the same machine **accumulates on the server onto the same code** (`quotaAmount = old + purchased`), expiry extends cumulatively (`base = max(now, old expiry) + pack validity`; perpetual codes stay perpetual), and `verify` / `activate` return the current total so the client doesn't sum anything; ② `NEW_CODE` — each order issues an independent new code while old codes stay valid; **each code is its own wallet** and the client spends from the code it holds. **Usage accounting is server-side**: report each consumption to §2.8 `POST /license/quota/consume`; the platform performs an atomic bounded decrement on the code's `quota_used` (`quota_used + amount <= quota_amount`), shares one balance across devices/reinstalls for the same code, and returns this code's `quotaUsed` / `quotaRemaining` as the trusted balance. `quotaAmount` / `quotaUsed` / `quotaRemaining` are `null` for EDITION products. QUOTA products must not call the upgrade endpoints (they change edition/period/expiry but never the quota) — the platform rejects them with `quotaUpgradeUseAddQuota`.

### 1.4 Field × pricing-model mapping (EDITION / QUOTA)

Each product picks one pricing model (product-level `licensePricingModel`). Not every field is meaningful for both models — read them per the table below (fields not applicable to a model are always `null`; render `-` defensively):

| Field | Model | Notes |
| --- | --- | --- |
| `licenseCode` / `machineCode` / `activationToken` / `status` | Common | License code / machine code / activation token / status (both models) |
| `productUniqueCode` / `source` / `maxMachines` / `activatedMachines` | Common | Product code / issue source / machine cap and bound count |
| `edition` | Common (differs in meaning) | EDITION: tier; QUOTA: always a single Basic edition (may be `null`) |
| `softwareMajorVersion` / `trialDays` / `trialExpiryTime` / `licenseDeductionEnabled` | EDITION | Major version / day-based trial / grace snapshot / upgrade proration |
| `billingPeriod` | **Dual meaning** | EDITION→subscription period (drives code `expiryTime` / renewal); QUOTA→per-lot validity period (per-lot `expires_at`) |
| `quotaAmount` / `quotaUsed` / `quotaRemaining` / `quotaNextExpiry` | QUOTA | Display total / used / remaining / quota expiry; **`quotaAmount` is always `null` for EDITION** |
| `trialCount` / `trialCountPeriod` / `trialPeriodKey` / `trialUsed` / `trialRemaining` / `trialNextResetTime` | QUOTA | Per-use trial quota / period / bucket key / used / remaining / next reset time; **always `null` for EDITION** (the trial dimension is mutually exclusive) |
| `consume` (`kind: 'quota' | 'trial'`) | QUOTA | Quota-consumption endpoint; EDITION never calls it |

### 1.5 General rules

- **Rate limit**: `activate` / `verify` count failures per IP + license code (10-minute window); over the limit returns `tooManyAttempts`. On receiving it, widen the retry interval — do not retry densely.
- **Verification cache**: `verify` results are server-cached (Cache API + KV); revoke/unbind/upgrade writes actively invalidate the cache, and a quota change (consume/addQuota) invalidates that code's cache across all its machines (quota is per-code); the SDK also keeps a 60s local cache (`verifyCached`). During a rollout window, older cache entries may lack `billingPeriod` — treat missing as `PERMANENT`.
- **Idempotency**: `software/generate` / `software/upgrade` are idempotent on "product + `clientOrderId`"; duplicate requests don't double-issue. `software/addQuota` is idempotent per order **when `clientOrderId` is sent**: the first call claims the key, a replay returns the first result instead of adding quota twice, and a concurrent duplicate gets `quotaOrderProcessing` (retry later — don't re-send under a new order id). The claim lives 7 days and an interrupted one self-releases after 2 minutes. Without `clientOrderId` the platform cannot de-duplicate (only the `timestamp` ±5-minute replay window applies), so repeat grants really do add quota again.
- **Replay protection**: a signed request's `timestamp` must be within 5 minutes of server time.

### 1.6 Signing (software/generate, software/upgrade)

**Payload** (fixed order, joined by `\n`):

```text
productUniqueCode 
 machineCode 
 edition 
 expiryDays 
 clientOrderId 
 licenseCode 
 billingPeriod 
 timestamp
```

- Fill missing fields with `''`; default `expiryDays` to `0`; normalize `billingPeriod` to trim + UPPERCASE (empty `''` for generate, which has no billing period)
- Signature: `HMAC-SHA256(licenseApiSecret, payload)`, Base64URL-encoded, put in the `signature` field
- `timestamp` is milliseconds
- Compatibility window: `billingPeriod` is now signed; during the transition the server still accepts the legacy 7-field signature that omits it, which will be rejected once existing clients upgrade

> **`software/addQuota` uses its own signing payload** (independent of the 8-field payload above, so existing SDKs are unaffected):
> ```text
> productUniqueCode 
> licenseCode 
> addAmount 
> quotaType 
> clientOrderId 
> edition 
> timestamp
> ```
> `quotaType` is normalized to trim + UPPERCASE (default `QUOTA`), `edition` defaults to `''`, `addAmount` is taken as-is (a positive number; decimals allowed); generated by the SDK via `signAddQuota` / `sign_add_quota`.

| Field | Type | Description |

| activatedAt | string | Activation time (ISO8601) |
| expiryTime | string/null | Expiry, `null` = perpetual |
| trialExpiryTime | string/null | Trial-expiry snapshot, non-`null` after trial-to-purchase |
| billingPeriod | string | `PERMANENT` / `MONTHLY` / `YEARLY`; legacy and trial codes are `PERMANENT` |
| quotaAmount | number/null | QUOTA: this code's display total (= Σ granted lot `cap`); the authoritative balance is `quotaRemaining`; `null` for EDITION/legacy/trial codes |
| quotaUsed | number/null | QUOTA products: this code's server-side accumulated used over live lots (`license_usage` lot aggregation, decremented by §2.8 `quota/consume`, shared across devices/reinstalls for one code); `null` for EDITION / non-QUOTA |
| quotaRemaining | number/null | QUOTA products: this code's remaining = Σ live-lot `max(0, cap - used)` (expired lots drop out); `null` for EDITION / non-QUOTA |

| trialPeriodKey | string/null | Server period key when reset-type (`DAILY`=YYYY-MM-DD, `WEEKLY`=ISO week YYYY-Www, `MONTHLY`=YYYY-MM, all UTC) — the server trial bucket key; otherwise `null` |

| trialExpiryTime | string/null | Trial-expiry snapshot |

| quotaAmount | number/null | QUOTA: this code's display total (= Σ granted lot `cap`); `null` for EDITION/legacy; cached with the result, older cache entries may omit it (treat as `null`) |
| quotaUsed | number/null | QUOTA products: this code's **server-side accumulated used over live lots** (`license_usage` lot aggregation, decremented by §2.8 `quota/consume`, shared across devices/reinstalls for one code); `null` for EDITION / older cache; cached with the result, invalidated per code across machines on consume, so it lags at most one TTL |

**Request**:

**Request**:

| Param | Type | Required | Description |
| --- | --- | --- | --- |
| productUniqueCode | string | yes | Product unique code |

### 2.5 In-app payment issuance (`/license/software/generate`, HMAC-signed)

**When**: after an in-app payment succeeds, called by the **software's server** (holding `licenseApiSecret`); the platform generates a code and pre-binds the machine. Idempotent on "product + `clientOrderId`". Billing period and quota are frozen onto the code: the platform writes `billingPeriod` and `quotaAmount` from the matched edition-config row (for editions with multiple period rows, pick one with `billingPeriod`; defaults to the edition's first row), consistent with the developer-issuance path.

| Param | Type | Required | Description |
| --- | --- | --- | --- |
| productUniqueCode | string | yes | Product unique code |
| machineCode | string | yes | Client machine code, ≥ 8 chars |
| edition | string | no | Chosen edition (must be in the product's edition config); defaults to the product default edition |
| expiryDays | number | no | Duration in days, 0/absent = perpetual; expiry is always computed from this parameter at issue time (the period is only a display/pricing key, it does not auto-derive duration) |
| billingPeriod | string | no | Target period: `MONTHLY` / `YEARLY` / `PERMANENT`; when one edition has multiple period rows, picks which to issue; defaults to the edition's first configured row; decides the frozen `billingPeriod` and QUOTA amount |
| clientOrderId | string | yes | In-app payment order ID (1–64 chars), globally unique |
| timestamp | number | yes | Milliseconds, valid within ±5 minutes |
| signature | string | yes | HMAC signature, see §1.6 |

**Success `content`**:

| Field | Type | Description |
| --- | --- | --- |
| licenseId | number | License record ID |
| licenseCode | string | Newly generated license code |
| productUniqueCode | string | Product unique code |
| edition | string/null | Edition |
| machineId | number | Pre-bound machine record ID |
| activatedAt | string | Activation time (ISO8601) |
| expiryTime | string/null | Expiry, `null` = perpetual |
| trialExpiryTime | string/null | Trial-expiry snapshot |
| billingPeriod | string | `PERMANENT` / `MONTHLY` / `YEARLY`; frozen onto the code from the matched edition-config row (defaults to the edition's first row, falls back to `PERMANENT` when no period config) |
| quotaAmount | number/null | QUOTA: `software/generate` freezes this pack's quota from the matched QUOTA config row and returns it; `null` for EDITION products (config row has no quota) and legacy |
| maxMachines | number | Max machines per code |
| activationToken | string | Activation credential, stored by the software |

**Error codes**: `productIdRequired`, `machineCodeInvalid`, `orderIdRequired`, `productNotFound`, `productNotEnabled`, `apiSecretMissing`, `signatureInvalid`, `productNotAvailable`, `orderAlreadyUsed` (same order already issued but machine not bound).

### 2.6 In-app upgrade/renewal (`/license/software/upgrade`, HMAC-signed)

**When**: after an in-app upgrade to a higher edition or a renewal, the software's server calls this, signed. Handled per the product's upgrade policy (`licenseUpgradeMode`):

- `SAME_CODE`: upgrade the edition on the original code and extend validity; machine bindings stay intact
- `NEW_CODE`: revoke the old code, issue a new one and migrate all machine bindings; re-issue a new `activationToken` for the current machine

> **QUOTA (usage-based) products must not call this endpoint**: upgrading only changes edition / billing period / expiry and **never touches `quotaAmount`**, so calling it on a quota product silently loses the quota (especially under `NEW_CODE`, where the new code carries no quota and the old one gets revoked). The platform rejects such calls with `quotaUpgradeUseAddQuota`. To grant more quota, have the user repurchase on the platform (accumulates automatically) or use §2.6.1 `software/addQuota`.

**Request**:

| Param | Type | Required | Description |
| --- | --- | --- | --- |
| productUniqueCode | string | yes | Product unique code |
| licenseCode | string | yes | The software's current license code (the original), ≥ 10 chars |
| machineCode | string | no | Client machine code; under `NEW_CODE` used to re-bind after migration and issue a new credential |
| edition | string | yes | Target edition (≤ 50 chars, must be in the product's edition config) |
| expiryDays | number | no | Renewal duration in days (0–3650); only lifetime editions honor this parameter's legacy behavior |
| billingPeriod | string | no | Target period: `MONTHLY` / `YEARLY` / `PERMANENT`; when one edition has multiple period rows, picks the upgrade target; defaults to the edition's first configured row |
| clientOrderId | string | yes | This order ID (idempotency) |
| timestamp | number | yes | Milliseconds, valid within ±5 minutes |
| signature | string | yes | HMAC signature, see §1.6 |

**Billing period & renewal extension**:

- Periodic (`MONTHLY` / `YEARLY`): new expiry = `max(now, old expiry)` + 1 period (consistent with the platform purchase flow)
- Lifetime (`PERMANENT`): stays perpetual; legacy software-issued custom-duration scenarios remain compatible with `expiryDays`

**Success `content`**: on top of the §2.5 fields, adds:

| Field | Type | Description |
| --- | --- | --- |
| upgraded | boolean | Always `true` |
| oldLicenseId | number | Returned only under `NEW_CODE`: the revoked old license record ID |
| machineId | number | `0` on the `SAME_CODE` idempotent-replay / lifetime-compat path |
| activationToken | string | A new credential only under `NEW_CODE` when the current machine re-binds successfully; otherwise an empty string |

**Error codes**: all of §2.5 plus `licenseCodeRequired`, `codeNotFound`, `revoked`, `quotaUpgradeUseAddQuota` (QUOTA product — repurchase or use `addQuota` instead).

### 2.6.1 In-app quota top-up (`/license/software/addQuota`, HMAC-signed)

**When**: for **QUOTA (usage-based)** license codes under the non-platform-collection (developer self-billing) scenario, to accumulate quota. Trial quota is added to `trialCount` and paid quota to `quotaAmount` (two independent pools). EDITION products do not use this (their tier changes go through `software/upgrade`).

**Signing**: uses the addQuota-specific payload (see §1.6); call it via the SDK's `addQuotaForSoftware` / `add_quota_for_software`.

**Request**:

| Param | Type | Required | Description |
| --- | --- | --- | --- |
| productUniqueCode | string | yes | Product unique code |
| licenseCode | string | yes | The code to top up (≥ 10 chars); a `T-` prefix routes to the Sandbox test table, otherwise the production table |
| addAmount | number | yes | Amount to add this call (positive number, decimals allowed, ≤ 1000000) |
| quotaType | string | no | `trial` (add to trial quota `trialCount`, edition unchanged) / `quota` (default, add to paid quota `quotaAmount`) |
| edition | string | no | Only honored for `quota`: moves the code to this paid edition while adding quota (`TRIAL` forbidden); ignored for `trial` |
| clientOrderId | string | recommended | Business order ID: the platform makes the grant **idempotent per order** on it (a replay returns the first result instead of adding quota twice); without it the platform cannot de-duplicate |
| timestamp | number | yes | Milliseconds, valid within ±5 minutes |
| signature | string | yes | HMAC signature (addQuota-specific payload), see §1.6 |

**Constraints & behavior**:

- Only codes in `ACTIVE` state that belong to this `productUniqueCode` on a QUOTA product can be operated on; in production the product must be listed and hold a license-service order.
- Expiry / billing period are unchanged; `quotaType=trial` does not change the edition.
- **Idempotency**: with `clientOrderId`, the platform claims the order key with a conditional KV write — first call writes `pending`, the result becomes `done` for 7 days, and a replay returns the first result without adding quota again; a concurrent duplicate gets `quotaOrderProcessing`, and an interrupted claim self-releases after at most 2 minutes. Without `clientOrderId` the platform does no order-level de-duplication (only `timestamp` replay protection), so repeat calls really do add quota again.
- On success the write invalidates this code's `verify` cache **across all its machines** so the next verify reflects the new balance (quota is per-code, so sibling codes don't need clearing); production triggers an ops audit alert.

**Success `content`**: the updated license record (with the new `trialCount` / `quotaAmount` and `edition`).

**Error codes**: `productIdRequired`, `licenseCodeRequired`, `productNotFound`, `productNotEnabled`, `apiSecretMissing`, `signatureInvalid`, `quotaAmountInvalid`, `editionRequired`, `codeNotFound`, `revoked`, `noPermission` (non-QUOTA product), `quotaOrderProcessing` (same order being processed concurrently — retry later).

### 2.7 Check for updates (`/product/updateCheck`, no login)

**When**: check at startup; on `hasUpdate=true` guide the user to the product detail page to download; degrade silently on network failure.

**Request**:

| Param | Type | Required | Description |
| --- | --- | --- | --- |
| productUniqueCode | string | yes | Product unique code |
| currentVersion | string | yes | Client's current version (≤ 64 chars) |

**Success `content`**:

| Field | Type | Description |
| --- | --- | --- |
| hasUpdate | boolean | Whether an update exists; `false` when the product is missing/unlisted/has no version |
| latestVersion | string/null | The product's latest version |

### 2.8 Quota consumption (`/license/quota/consume`, no login)

**Applies to**: usage-based (QUOTA) products only. It lifts "how much has been used" out of the client's local storage and onto the server, curing the **multi-fold consumption caused by one license code holding an independent local counter on each browser / laptop / after reinstall**: usage now lives in the server's `license_usage` lots/buckets table, shared across devices. Paid quota is granted as **lots** — each carries its own `cap` + `expires_at`; consumption deducts from the **earliest-expiring live lot first (FIFO)** among unexpired lots with room, and `remaining = Σ (cap - used)` over live lots. Trial quota is accounted in server period buckets (`kind=trial`). **The code is never marked `expired` by quota**: exhausting or expiring all lots only drives `remaining=0` to prompt repurchase.

**When to call**: report a deduction each time the user consumes quota (e.g. one paid feature invocation). The client **must stop relying on a local count for gating** and instead treat `quotaRemaining` (from this response, or from startup `verify`) as the only trusted balance.

**Auth**: same family as §2.2 `verify` — HMAC of `activationToken` + machine binding (the `machineId` in the token) + valid license; **it does not read the `verify` cache** (it needs live quota). Production requires the product to be listed.

**Request**:

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| licenseCode | string | yes | License code, ≥10 chars (`T-` prefix routes to Sandbox) |
| machineCode | string | yes | Current machine code (extension Install ID for plugins), ≥8 chars |
| activationToken | string | yes | Credential issued at activation, ≥20 chars |
| amount | number | yes | Units consumed this call; positive number, decimals allowed (e.g. 0.5 for token/time metering; single-call cap 1,000,000) |
| requestId | string | recommended | Client idempotency key, 8–128 chars; required to prevent duplicate deduction on retries |
| kind | string | no | Consumption type: `quota` (default, deduct paid quota lots) / `trial` (deduct the trial period bucket); omitted → `quota` |

**Success `content`**:

| Field | Type | Notes |
| --- | --- | --- |
| consumed | number | Units actually deducted this call |
| kind | string | Consumption type this call (`quota` / `trial`, echoing the request) |
| quotaUsed | number/null | Paid quota: accumulated used over live lots (server lot aggregation) |
| quotaRemaining | number/null | Paid quota: Σ live-lot `max(0, cap - used)`; **gate on this**, route the user to the pricing page when it hits 0 |
| trialUsed | number/null | Trial quota: current period bucket used (server-accounted) |
| trialRemaining | number/null | Trial quota: current period bucket remaining; `null` when `trialCount` is disabled |
| trialNextResetTime | string/null | Trial quota: current period bucket's next reset time (reset-type period derived); `null` for `TOTAL`/disabled |

**Idempotency** (only when `requestId` is sent): a KV conditional-write claim keyed on (env + license code + `requestId`), with the **opposite** semantics of addQuota (a replay must not deduct again — that would hurt the user): the first call deducts and stores the result, a replay returns the first result without deducting, a concurrent duplicate gets `quotaConsumeProcessing`, and business failures such as insufficient quota store no idempotency result (the claim is released so a smaller amount can be retried under the same `requestId`). Without `requestId` the platform cannot de-duplicate (logged only), so client retries may deduct more than once — the caller must guarantee idempotency.

**No over-draw under concurrency**: the deduction picks live (unexpired, with room) lots in FIFO order and applies a per-lot atomic bounded UPDATE (only when `used + take <= cap` and the lot is unexpired); a concurrent request that would exceed the balance matches 0 rows → the shortfall re-fetches lots and re-allocates (up to 3 passes); if nothing lands → `insufficientQuota`. Every successful deduction writes one `license_quota_txn` row (recording `kind`/`bucket_key`/`amount`; a unique `(license_id, request_id)` index as a second idempotency guard).

**Balance & cache**: quota is **per-code** (one code shares a single ledger across devices/reinstalls; `consume` deducts only the current code's lots, never a sibling on the same machine), so `quotaUsed`/`quotaRemaining`/`trialUsed`/`trialRemaining` in the response are all aggregated server-side from `license_usage` (`license.quota_amount` is only a display total). `verify` caches these aggregated balances, and `consume` invalidates them per code across machines, lagging at most one TTL (~30 min) — so the `consume` immediate return is the freshest value. **Trial quota (`trialCount`) is now server-accounted in period buckets** (`kind=trial`): a new period naturally opens a new bucket → the old one resets to zero on its own, no longer relying on the client-local counter.

**Boundary (honest)**: server-side accounting only "raises the cheating cost and leaves an audit trail" — it **cannot** stop a purely-local feature plugin that simply never calls `consume` (if the feature works without any server response, nothing gates it). It stops multi-fold consumption naturally only when the feature genuinely needs a server capability (AI inference, cloud resources, etc.).

**Error codes**: `tokenInvalid`, `machineNotActivated`, `invalidOrRevoked`, `expired`, `productNotEnabled`, `productNotAvailable`, `noPermission` (non-QUOTA product), `quotaAmountInvalid` (invalid/over-cap amount), `insufficientQuota`, `quotaConsumeProcessing` (same request in flight, retry shortly), `tooManyAttempts`.

## 4. Cautions

- **Keep the secret server-side only**: signing can only happen on your software's server; a leaked client-side secret equals a broken licensing system.
- **Machine-code stability**: prefer the SDK's `machineCode()` (persisted UUID → hardware serial → system ID → composite-signal fallback). If an OS reinstall changes the machine code, unbind in the profile center first, then re-activate.
- **Minimize local credentials**: the client stores only `licenseCode + activationToken + the last verify result`; persist no other license data.
- **Trust the platform for validity**: `expiryTime`, edition and machine limits are as returned by the platform; never relax them client-side.
- **Billing-period display**: `billingPeriod` is frozen by the platform at purchase/upgrade and delivered in responses; clients only display it, never derive expiry from it.
- **Environment isolation**: Sandbox test codes carry the `T-` prefix; activate/verify/unbind auto-route to the test tables. `activationToken` embeds the environment, so cross-env use is rejected with `tokenInvalid`.
